# Соглашения по коду

Правила, которых держимся в этом проекте. Если правка нарушает одно из них —
либо не делай, либо объясни почему.

## Железные правила

### 1. Управление не трогаем без просьбы

Логика полёта дрона и управление игроком подобраны вручную, на ощупь. Код может
выглядеть «неправильным» (магические знаки, странные пороги) — это настройка под
ощущение игры, а не недосмотр.

**Нельзя** переписывать схему управления, потому что «так правильнее». Если просят
доработать — меняй по одному месту внутри существующей схемы и объясняй, что
трогаешь, до правки. Подробнее: [Дрон](drone.md#правило-не-переписывать-управление).

### 2. Состояние игры — не в ScriptableObject

ScriptableObject в Unity это **ассет**: всё, что в него записали в рантайме,
остаётся в файле после выхода из play mode (в редакторе) и переживает перезагрузку
сцены (в сборке). Поля-флаги в SO уже сломали квесты и счётчик дней —
см. [Известные проблемы](known-issues.md#p1-3-состояние-игры-живёт-в-ассетах).

SO — только для **конфигурации на чтение**: кривые, цены, тексты, ссылки на префабы.

### 3. Проверять, а не предполагать

«Скомпилировалось» ≠ «работает». Перед тем как сказать «готово», проверь то, что
реально изменилось. Доступные способы — ниже.

### 4. Пушить в `main`

Веток и PR не заводим. Коммит → `git push origin main`.

## Стиль кода

### Именование

В проекте много опечаток в именах типов и полей (`Interract`, `PlayerControll`,
`BsseManager`, `PhpBarController`, `MineableResourses`, `firstBotCrea6ted`).
**Новые** сущности называем правильно; старые переименовываем только отдельной
задачей — переименование типа рвёт связи в префабах и сценах.

| Что | Как |
|---|---|
| Классы, методы, свойства | `PascalCase` |
| Поля приватные | `camelCase` |
| Константы | `PascalCase` |
| Булевы поля | с префиксом состояния: `isDying`, `hasTarget` |

### Поля в инспекторе

Предпочитаем `[SerializeField] private` вместо `public`. Публичное поле — часть
контракта типа; если его меняет только инспектор, оно не должно быть публичным.

### Комментарии

Пишем **почему**, а не **что**. Хороший пример — пояснения в
[`DroneControl.cs`](../Assets/Scripts/Drone/DroneControl.cs): они объясняют модель
управления и смысл знаков, а не пересказывают строки.

Комментарии на русском и английском сейчас смешаны. Новые — на языке файла, в
который пишешь; в пределах одного файла не мешать.

### Чего избегать

| Антипаттерн | Почему | Чем заменить |
|---|---|---|
| `FindAnyObjectByType` в `Start`/`Update` | скрытая зависимость, ломается молча | ссылка через `[SerializeField]` |
| `GameObject.Find("Имя")` | ломается от переименования объекта | то же |
| `Camera.main` каждый кадр | лишний поиск, 8 мест в проекте | закешировать в `Awake` |
| `async void` | исключения теряются, нет отмены | `async Awaitable` + `destroyCancellationToken` |
| Операции с `Cursor.lockState` в разных скриптах | три владельца конфликтуют | один владелец, см. [план](architecture-plan.md) |
| Магические строки аниматора (`"Run"`, `"Hit"`) | опечатка не ловится компилятором | `Animator.StringToHash` в статическом поле |

## Проверка изменений

### Компиляция без Unity

Быстрая проверка синтаксиса и API одного-двух скриптов Roslyn'ом, не дожидаясь
редактора:

```bash
U="/c/Program Files/Unity/Hub/Editor/6000.3.19f1/Editor/Data"; M="$U/Managed/UnityEngine"
dotnet "$U/DotNetSdkRoslyn/csc.dll" -target:library -nostdlib -noconfig -out:/tmp/out.dll \
 -r:"$U/NetStandard/ref/2.1.0/netstandard.dll" \
 -r:"$M/UnityEngine.CoreModule.dll" -r:"$M/UnityEngine.UIElementsModule.dll" \
 -r:"$M/UnityEngine.PhysicsModule.dll" -r:"$M/UnityEngine.InputLegacyModule.dll" \
 -r:"$M/UnityEngine.AnimationModule.dll" -r:"$M/UnityEngine.AIModule.dll" \
 Assets/Scripts/<файл>.cs
```

Если тип тянет зависимости, которых нет в списке, — подставь заглушки во временной
папке, а не выключай проверку.

Эта проверка однажды поймала реальную поломку сборки: `using UnityEngine.UIElements`
делает `Cursor` неоднозначным (в UI Toolkit есть свой `Cursor`), и
[`DroneControl.cs`](../Assets/Scripts/Drone/DroneControl.cs) перестал компилироваться.

### Проверка в живом редакторе

Unity открыт на папке проекта, MCP-сервер `UnityMCP` подключён. Через него можно:

- `read_console` — ошибки компиляции и рантайма (**делай это после каждой правки скрипта**)
- ресурс `mcpforunity://editor/state` — идёт ли компиляция, какая сцена открыта
- `manage_editor` с `play`/`stop` — запустить сцену и посмотреть поведение
- `manage_scene`, `find_gameobjects` — проверить, что компоненты реально связаны

После правки скрипта Unity перекомпилирует проект; дождись `isCompiling: false`,
прежде чем делать выводы.

### Правка YAML сцен и префабов вручную

Иногда быстрее отредактировать `.unity`/`.prefab` текстом, чем кликать в редакторе.
Тогда:

- `fileID` компонентов **не выдумывать** — брать из реального примера
  (`Library/PackageCache/.../*.unity`) или из самого проекта;
- после правки проверять, что не осталось висячих ссылок на удалённые `fileID`
  и что объект прописан в `SceneRoots`;
- **Unity должен быть закрыт или сцена переоткрыта** — иначе редактор перезапишет
  правки своей версией из памяти.

## Git

- Пушим в `main`.
- `UIElementsSchema/` в корне — генерируемая Unity схема для автодополнения,
  в репозиторий не коммитим.
- `Packages/packages-lock.json` **коммитим** — он фиксирует точный коммит
  git-пакетов.
- Правки ассетов (`.unity`, `.prefab`, `.asset`) делаем при закрытом редакторе
  либо сразу проверяем, что Unity их не перезаписал.
