# Архитектурный план

План перехода от текущего состояния к структуре, которая выдержит рост проекта.
Рассчитан на то, что разработка продолжается — поэтому разбит на этапы, каждый из
которых оставляет игру рабочей.

## Где мы сейчас

**Что хорошо:** механики работают и играются; `StatsHandler` — удачная единая
модель здоровья на событиях; `ResourceController` правильно разложен на
абстракцию и наследников; `AllResources` как единый тип валюты — верное решение;
Unity Behavior снимает квестовую логику с кода; новый HUD дрона показывает
правильный образец (владелец данных отдаёт их геттерами, UI только читает).

**Что мешает расти:**

| Проблема | Во что выливается |
|---|---|
| Связи через `FindAnyObjectByType` и синглтоны | зависимости не видны, ломаются в рантайме молча |
| Состояние в ScriptableObject | прогресс «залипает» между сессиями |
| Одна сборка `Assembly-CSharp` | полная перекомпиляция на любую правку |
| Нет тестов | даже чистую логику (`AllResources`) проверить нечем |
| Ввод размазан по десятку скриптов | нельзя переназначить клавиши, конфликт режимов |
| Два UI-стека | одна и та же панель живёт в двух мирах |

## Целевая структура

Разделение на слои, где **зависимости идут только вниз**:

```
┌─────────────────────────────────────────────┐
│  Presentation    HUD, панели, полоски HP     │  UI Toolkit, читает модель
├─────────────────────────────────────────────┤
│  Gameplay        игрок, боты, враги, дрон,   │  MonoBehaviour-ы сцены
│                  строительство, волны         │
├─────────────────────────────────────────────┤
│  Services        ресурсы, прогресс, ввод,    │  обычные C#-классы,
│                  поиск целей, время           │  создаются композитным корнем
├─────────────────────────────────────────────┤
│  Domain          AllResources, Fraction,     │  чистый C#, без UnityEngine,
│                  Health, QuestState           │  покрывается тестами
└─────────────────────────────────────────────┘
```

Ключевой принцип: **UI ничего не знает о том, кто его читает, а модель ничего не
знает об UI**. `DroneStatsController` уже так устроен — он спрашивает данные у
владельца через геттеры и рисует их; это образец для остальных панелей.

### Композитный корень вместо синглтонов

Сейчас: `StoredResources.instance`, `GameManager.instance`,
`FindAnyObjectByType` в восьми файлах.

Цель: один объект на сцене (`GameBootstrap`), который в `Awake` создаёт сервисы и
раздаёт их тем, кому они нужны, — через `[SerializeField]`-ссылки или явную
инициализацию. Зависимость становится видна в инспекторе и не может потеряться
молча.

Полный DI-контейнер здесь не нужен — проект маленький, хватит явной сборки.

## Этапы

Порядок выбран так, чтобы сначала поставить страховку, потом чинить опасное,
потом трогать структуру.

### Этап 1. Страховка

Без неё любой следующий этап — риск.

1. **Сборки.** Добавить `asmdef`: `Game.Domain` (без ссылок на Unity),
   `Game.Services`, `Game.Gameplay`, `Game.UI`. Это ускорит компиляцию и —
   главное — **сделает нарушения слоёв ошибкой компиляции**, а не вопросом
   дисциплины.
2. **Тесты.** Подключить Test Framework (уже в зависимостях), первые тесты — на
   `AllResources`: операторы сравнения, сложение, вычитание. Это чистый C# без
   сцены, тестируется мгновенно и уже содержит баг (P0-1).
3. **`.gitignore`** — дописать `UIElementsSchema/`.

**Результат:** есть куда писать тесты и чем ловить развал слоёв.

### Этап 2. Состояние игры: из ассетов в рантайм

Чинит [P1-3](known-issues.md#p1-3-состояние-игры-живёт-в-ассетах) — самую дорогую
из проблем.

Разделить то, что сейчас слито в ScriptableObject:

```
QuestDefinition (SO, только чтение)      QuestState (runtime)
├── dialogData                           ├── isTaken
├── условие выполнения                   ├── rewardGained
└── награда                              └── currentIndex
```

Состояние всех квестов держит сервис `QuestProgress`, живущий сцену. Узлы графа
Behavior получают его через blackboard, а не лезут в ассет.

То же самое для `TimePeriod` (вынести `dayNumber`/`currentProgress` в
рантайм-объект) и для event-каналов (`countNPC`, `firstBotCrea6ted` — в
`GameProgress`, не в канал).

Заодно: свести три флага прогресса (`firstBuildCreated`, `firstKillMaded`,
`firstBotCrea6ted`) в один `GameProgress` — сейчас они живут в двух разных местах.

**Проверка этапа:** пройти квест, выйти, зайти снова — квест должен начаться
заново.

### Этап 3. Ввод и режимы

Чинит [P1-4](known-issues.md#p1-4-три-владельца-курсора) и готовит почву под
[P2-8](known-issues.md#p2-8-устаревший-input-manager).

1. Ввести понятие **режима ввода**: `Gameplay`, `Building`, `UI`, `Drone`.
   Один сервис `InputMode` владеет текущим режимом и **единолично** управляет
   `Cursor.lockState`/`visible`. Остальные просят смену режима, а не трогают
   курсор сами.
2. Клавиши собрать в одно место (`InputMap`), вместо `KeyCode` по всему коду.
3. Отдельным шагом — миграция на Input System. Делать **после** шага 1, иначе
   переносится та же каша.

**Проверка:** открыть магазин → панель строительства → сесть в дрон → выйти;
курсор каждый раз в верном состоянии.

### Этап 4. Бой и урон

Чинит [P0-2](known-issues.md#p0-2-ondeath-срабатывает-многократно) и
[P2-2](known-issues.md#p2-2-четыре-разных-способа-нанести-урон).

1. **Флаг смерти** в `StatsHandler` — первым делом, это однострочная правка с
   большим эффектом.
2. Один компонент `DamageDealer` вместо четырёх скриптов: настраиваемые урон,
   цель (по фракции — **один** критерий), период повторного срабатывания.
   Фракцию сделать единственным способом определять «свой/чужой», компонент
   `Enemy` оставить только маркером типа ИИ.
3. Урон лучом из `DroneShooting` обобщить в переиспользуемый `HitscanWeapon` —
   он уже написан правильно (ищет компоненты в родителях, бьёт по видимой
   траектории).

### Этап 5. ИИ и поиск целей

Чинит [P0-3](known-issues.md#p0-3-враги-каждый-кадр-обыскивают-всю-сцену),
[P1-1](known-issues.md#p1-1-общий-таймер-ломает-выбор-целей),
[P1-2](known-issues.md#p1-2-падение-при-дубликате-цели).

Заменить поиск по сцене **реестром**: каждый потенциальный объект-цель при
включении регистрируется в `TargetRegistry`, при выключении снимается. Поиск цели
становится проходом по короткому списку вместо `FindObjectsByType`/`OverlapSphere`.

Выбор цели вынести в сервис:

```csharp
Transform FindBest(Vector3 from, float radius, IReadOnlyList<TargetPriority> priorities);
```

Один проход, все типы сразу, одна общая формула `priority / distance`, никаких
таймеров на каждый тип и никаких словарей с риском дубликата.

Там же: удалить дублирующий `BotNavigation`
([P2-3](known-issues.md#p2-3-дублирующая-логика-добычи)) и починить
`Update` в `NPCFacade` на `virtual`/`override`.

**Проверка:** волна из 30+ врагов без просадки кадров; враг переключается между
игроком, ботами и турелями по приоритетам.

### Этап 6. Интерфейс

Добить переход на UI Toolkit, начатый с HUD дрона.

Порядок — от простого к сложному:

1. Запасы ресурсов и часы (просто текст) — заодно снимает с `StoredResources`
   обязанность рисовать.
2. Панель строительства и магазин (кнопки, списки).
3. Диалоги.

Мировые полоски HP над NPC **оставить на uGUI** — это осознанное исключение,
UI Toolkit плохо работает с world-space.

Каждая новая панель — на классах из [`Cyberpunk.uss`](../Assets/UI%20Toolkit/Cyberpunk.uss),
чтобы интерфейс остался единым.

### Этап 7. Уборка

Делать в конце, чтобы не ломать ориентиры по дороге:

- удалить мёртвые файлы ([P3-1](known-issues.md#p3-1-мёртвые-файлы));
- вычистить мусорные `using`;
- исправить опечатки в именах — **по одной**, с проверкой связей в сцене;
- мелочи из [P3-4](known-issues.md#p3-4-прочее).

## Чего в плане намеренно нет

- **Сохранение/загрузка игры.** Этап 2 — предпосылка к нему (состояние станет
  отделимым от ассетов), но сам сейв в план не входит: сначала нужно, чтобы
  состояние вообще было в одном месте.
- **Сетевая игра.** Текущая архитектура к ней не готова, и закладываться не стоит,
  пока нет такой цели.
- **Пулинг объектов.** Нужен, когда волны станут большими; до этого —
  преждевременная оптимизация. Реестр целей из этапа 5 к нему подготовит.
- **Полный DI-контейнер.** Для 83 скриптов явная сборка в композитном корне
  проще и понятнее.

## Как пользоваться планом

Этапы 1–2 стоит сделать подряд: первый даёт страховку, второй чинит самое
дорогое. Дальше порядок можно менять под то, какие механики сейчас в работе —
но **этап 5 не начинать раньше этапа 1**: переделка ИИ без тестов и без границ
сборок слишком легко ломает поведение незаметно.

Каждый этап заканчивается проверкой в играющей сцене, а не только компиляцией.
Unity открыт и подключён по MCP — значит, play mode и консоль доступны прямо из
агента, см. [Соглашения](conventions.md#проверка-в-живом-редакторе).
